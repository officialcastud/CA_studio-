## How each rule was driven

Three harnesses, all Playwright against the assembled form:

1. **Engine-driven** — inject a variant of `tests/ITR-5/state.js`, `paint()`, then
   `runRules(Object.values(buildReturn().ITR)[0], S)`. Used wherever the form's own inputs
   can actually produce the violation (HP co-ownership, unrealised rent, C49 nature,
   presumptive-vs-BS, residence gates, the ICDS→OI→BP feed).
2. **Crafted return** — take the lawful `buildReturn()` object, deep-clone, apply a targeted
   mutation, call `runRules(craftedReturn, S)`. This is the right tool for the BP ladder:
   A6/A9/A10/A13/A26/A33/A34/A36/A37/B42/C46/C48/D and the OI/ESR feeds are **engine-computed
   totals**, so the form can never emit them inconsistent — those rules exist to catch a
   hand-edited or portal-supplied return, and that is exactly how they were driven.
3. **Schedule-absence probe** — `{}`, `null`, and the return with `ScheduleHP` /
   `CorpScheduleBP` / `PARTA_OI` / `ScheduleESR` / `SchedulePTI` removed, to prove the batch
   is a silent no-op rather than a thrower.

**Baseline:** the unmodified reference return fires **0** Category-A rules (whole rule set, not
just this range) and raises no page error. Every "silent-on-lawful" column below is measured
against that baseline plus, for every conditional rule, a *populated-but-lawful* variant on the
open side of the guard.

Totals run: **182 crafted cases** (99 violation / 83 lawful), **19 engine-driven state variants**,
**7 engine-driven ICDS-feed variants**, **10 schedule-absence shapes**.

## FAILS

### **239 — "value at field 11 (Depreciation and amortization debited to P&L) should be equal to sl.no.53 of P&L A/c + sl.no.1E(vi) of Manufacturing A/c"**

**Does not fire on a violation that the form itself produces.**

The encoding (`61_rules_enc_05.js`) replaces the equality with a *range*:

```js
A(239, a11 >= pl53-1 && a11 <= pl53+mfg+1, …)
```

so any A11 anywhere between `PL 53` and `PL 53 + Mfg 1E(vi)` passes. The manufacturing-account
depreciation is therefore never actually required to be in A11.

**Exact scenario (the reference client itself, no mutation needed):**

| figure | path | value |
|---|---|---|
| BP A11 | `CorpScheduleBP.BusinessIncOthThanSpec.DepreciationDebPLCosAct` | 400,000 |
| P&L 53 | `PARTA_PL.DebitsToPL.DebitPlAcnt.DepreciationAmort` | 400,000 |
| Mfg 1E(vi) | `ManufacturingAccount.OpeningInventory.DeprctnOfFactoryMachinery` | 60,000 |
| rule text requires | 53 + 1E(vi) | **460,000** |

`runRules()` on `tests/ITR-5/state.js` → **serial 239 is silent**, although A11 (400,000) is
60,000 short of what the rule's own text demands.

Second, scaled demonstration (engine-driven, `S.pl.mfg.OpeningInventory.DeprctnOfFactoryMachinery = 200000`):
A11 = 400,000, text requires 600,000 → **still silent**. The gap widens with 1E(vi) and is never caught.

The rule *does* fire outside the window (A11 = 600,000 with 1E(vi) = 60,000 → fires;
A11 = 300,000 → fires), so it is not dead — it is **under-tight in exactly the direction the
rule text states**, and the shipped reference return is itself an undetected violation.

Note the encoder's own comment says the range was chosen because "the reference test state sets
item 11 = P&L 53 only". But `books/ITR-5/BP.md` line 79 gives A11 as a *computed* cell:
`K65 = MAX(PL.DepreciationAmort + ManuFactureAcc_DepreciationOfFactoryMachinary, 0)`.
So the reference state (`S.bp.depDebPL = 400000`) is the thing that is wrong, not the rule —
the fix belongs in two places:
- `70_sec_bp.js` — A11 is currently a free input (`put(j,P+"DepreciationDebPLCosAct",n0(B.depDebPL))`)
  where the book says it is computed from P&L 53 + Mfg 1E(vi);
- `61_rules_enc_05.js` — restore the exact equality `REQ(a11, pl53 + mfg)` once A11 is computed.

## Notes / residual observations (not FAILs)

- **N1 · 225 / 229 — the ICDS → OI → BP feed. Both verified end-to-end through the engine, both PASS.**
  Chain: `Schedule ICDS` col XI(3)/XI(4) → auto-populates `PARTA_OI` 3a/3b
  (`ProfDeviatDueAcctMeth` / `DecProOrIncLossUs145_2`, `70_sec_oi.js` L95-96) → and BP computes
  A25 = `max(0, S.bp.i25 + ICDS increase)`, A32 = `max(0, S.bp.i32 + ICDS decrease)`.
  OI 4d/4e (the 145A part) and BP `i25`/`i32` are **two independent filer inputs**, so a real
  filer can enter the 145A figure in Part A-OI and forget it in BP — which is precisely the
  mismatch these two rules exist to catch. Engine-driven evidence:

  | variant | OI 3a/3b/4d/4e | BP A25 / A32 | rules fired |
  |---|---|---|---|
  | ICDS 25k inc + 40k dec, 145A 10k/5k entered in both OI and BP | 25000 / 40000 / 10000 / 5000 | 35000 / 45000 | none |
  | same, but BP `i25` left 0 | 25000 / 40000 / 10000 / 5000 | 25000 / 45000 | **225** |
  | same, but BP `i32` left 0 | 25000 / 40000 / 10000 / 5000 | 35000 / 40000 | **229** |
  | ICDS empty, no 145A anywhere | 0 / 0 / 0 / 0 | 0 / 0 | none |
  | ICDS decrease only (40k) | 0 / 40000 / 0 / 0 | 0 / 40000 | none |
  | BP `i25` inflated to 15k with OI 4d = 0 | 25000 / 0 / 0 / 0 | 40000 / 0 | **225** |

  Both rules also fire correctly on a hand-edited return in either direction (OI side zeroed,
  OI side inflated, BP side zeroed) and are silent when `PARTA_OI` is absent.
- **N2 · 225 and a negative OI 4d.** If a filer types a *negative* 4d (−50,000) with ICDS 3a = 25,000,
  the BP engine clamps A25 to `max(0, −25,000) = 0` while the rule's right-hand side is −25,000, so
  225 fires. The return is genuinely malformed (a decrease belongs at 4e, not a negative 4d), so the
  firing is right — but the message points at BP A25 rather than at the negative OI entry, and the
  form currently accepts a negative 4d at all. Input-validation seam, not a rule defect.
- **N3 · guard shape on the OI-fed rules (218-222, 225, 227-229, 245).** All nine sit inside
  `if(I.PARTA_OI)`. A return that omits Part A-OI entirely leaves the BP A14-A18/A25/A29/A30/A32/A8b
  figures completely unchecked. This matches each rule's own text ("…should be equal to <x> of
  Part-OI") and the same shape is used for 203 (`!I.SchedulePTI ||`), 209/210/211, 226. Flagging as a
  known, text-faithful gap rather than a defect.
- **N4 · 238 is a presence-parity proxy, not an amount match.** The rule text says A4a "should match"
  A35; the encoding asserts *a section is non-zero at A4a iff it is non-zero at A35*, because the two
  boxes are unequal by tax logic (book profit removed vs deemed income added). Verified: fires when
  only one side is declared (engine-driven, both directions), silent when both are. Residual risk: a
  genuine 44AD/44AE filer whose book profit for that business is exactly nil would have A4a = 0 with
  A35 > 0 and would see 238 fire. Worth a second look if the CEO wants a tighter reading.
- **N5 · rules.json text wrapping.** Serials in this range carry PDF line-wrap spill (e.g. 239's text
  ends "…should be" and 240 opens "equal to sl.no.53 of P&L + 1E(vi)… Schedule BP … field A39 …").
  The encoder split each wrapped pair one-check-per-serial, which is the sensible reading and is what
  was tested. Serials whose text begins mid-sentence (i.e. carry the tail of the previous serial):
  **206, 208, 209, 213, 217, 234, 240, 242, 243, 247, 249** — 11 wrapped pairs in this range alone.
- **N6 · 249 covers both routes.** The 115BBF check catches BP `IncRecCredPLOthHeadDtls.UnderSec115BBF`
  and any `ScheduleSI.SplCodeRateTax` row whose code matches `/5BBF/` — i.e. `5BBF` (other sources),
  `5BBF_BP` (business) and `PTI_5BBF`. It is outside the `if(I.CorpScheduleBP)` block, so it still
  fires on an NRI return that carries 115BBF in Schedule SI only, with no BP schedule at all. Verified.
- **N7 · 237 matches the engine, not the literal text.** The encoding uses
  `max(0,C48) + max(0,B42) + A37`, identical to `70_sec_bp.js` L342 (`D = MAX(0,C48)+MAX(0,B42)+A37`).
  A speculative-loss return computed the engine's way is silent; the same return with D computed
  literally as `A37 + B42 + C48` fires. Correct on both sides.
- **N8 · 203 / 205 / 206 are hand-edit guards only.** The engine auto-feeds Schedule HP item 2 from
  Schedule PTI (`70_sec_other.js` L109) and derives 1(h) from the 24(b) loan rows
  (`70_sec_hp.js` L147), so the form cannot emit these violations. Driven as crafted returns
  (a portal-supplied / hand-edited JSON), which is what they guard against; engine-driven lawful
  variants confirm silence.
