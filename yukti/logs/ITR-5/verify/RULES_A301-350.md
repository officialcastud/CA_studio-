## Method

Two harnesses, both driving the real assembled form in Chromium via Playwright.

1. **Crafted-return harness** (`runRules(craftedI, S)`). Load the form, inject the lawful
   reference client `tests/ITR-5/state.js`, `paint()`, take `I = Object.values(buildReturn().ITR)[0]`,
   then deep-clone `I` and apply a per-case mutation list before calling `runRules(I, S)`.
   This is the route the brief sanctions for the hand-edited/portal-supplied returns that
   the engine itself can never emit — and the whole of 301–350 is of that kind, because
   Schedules DEP and DCG are **entirely computed** from DPM/DOA (`books/ITR-5/DEP_DCG.md`:
   "every cell here is computed — nothing is keyed on this sheet"), so the engine cannot
   produce a DEP/DCG roll-up that disagrees with itself.
   105 crafted cases in total (74 + 31).
2. **Engine harness**. All 62 engine-producible scenario states in `tests/ITR-5/verify/`
   (`re_*.js` full states across firm / LLP / AOP / co-op / AJP / business-trust / local
   authority × old / new / 115BAD / 115BAE / 115TD, and `sc_*.js` patches on the reference
   client) run end-to-end through the form, rules read off the built return.

**Lawful reference results.** `tests/ITR-5/state.js` (resident firm, OLD regime) builds all
six relevant schedules — DEP, DCG, DPM, DOA, ESR, CG — and `runRules` returns **0 rules of
any category**. Across all 62 scenario states (9 of which build all six schedules)
**no serial in 301–350 fired once**. Baseline false-firing: none.

**Lawful-with-data reference ("RICH").** Because the reference client leaves many blocks at
zero (DEP 1b/1c/1d = 0, all of DCG = 0, ESR rows ii–ix = 0, LTCG B1/B3/B6/B8 absent), a
zero-valued pass is a weak silence test. So every violation case is built on a hand-made
*lawful* return in which every leaf each rule reads is non-zero and internally consistent:
DPM Rate15/30/40/45 and DOA Building 5/10/40 + furniture + intangible + ships all carry
distinct net-aggregate, proportionate and s.50 figures; DEP and DCG roll them up exactly;
ESR carries nine non-zero rows; CG carries A1/A3/A5/A6 and B1/B3/B6/B8 with live
consideration and s.48 figures plus a full table E. That RICH return is **silent on every
serial in 301–350** (case `L01_rich_all`). Each violation case is then RICH **plus a single
targeted perturbation**, so the paired L/V design isolates the exact field each rule bites on.
The `dpmDep` "17i **or** 18i as applicable" branch is exercised on both sides: DPM Rate40 and
DOA Building Rate40 carry a non-zero `ProportionateAggDepreciation` (the Sl.18/15 branch),
the rest use `NetAggregateDepreciation` (the Sl.17/14 branch).

Tolerance note: `REQ(a,b,tol)` defaults to `tol = 1`, so a rule cannot fire on an off-by-one.
Every perturbation used here is ≥ 5,000, well clear of that band.

## Guard gaps — the three things the CEO should look at

These are not FAILs of the comparison itself (every one of the 22 fires correctly when both
schedules are present and disagree). They are cases where the **schedule-presence guard is
wider than the rule text**, so a hand-edited or portal-supplied return that violates the rule
by *omitting the counterpart schedule* passes silently. Each is reproduced below.

### G1 — `if(I.ScheduleDPM)` suppresses 303–306 and 316–319
`61_rules_enc_07.js` wraps the DEP↔DPM and DCG↔DPM comparisons in `if(I.ScheduleDPM)`.
**Scenario (case `GA_noDPM_depclaimed`):** a return carrying
`ScheduleDEP.SummaryFromDeprSch.PlantMachinerySummary` = {1a 375000, 1b 60000, 1c 45000,
1d 90000, 1e 570000} and `ScheduleDCG…PlantMachinerySummaryCG` = {1b 7000, 1c 8000, 1d 9000},
with the `ScheduleDPM` key **deleted entirely**. Rule text 303 requires DEP 1a to equal
"sl no 17i or 18i of schedule DPM"; with no Schedule DPM those are nil, so 375000 ≠ nil is a
violation. Result: **serials 303, 304, 305, 306, 316, 317, 318, 319 all stay silent.**
A control (`GA_noDPM_v303`) confirms the guard, not the data, is doing the suppressing: the
same return with DPM present and Rate15 net aggregate = 999999 fires 303.

### G2 — `if(I.ScheduleDOA)` suppresses 307–312 and 320–325
Same shape, DOA side. **Scenario (case `GA_noDOA_depclaimed`):** `ScheduleDEP` carrying
2a 50000, 2b 30000, 2c 22000, furniture 20000, intangible 25000, ships 12000 and `ScheduleDCG`
carrying 2a 5000, 2b 3000, 2c 4000, furniture 2000, intangible 2500, ships 1200, with
`ScheduleDOA` **deleted**. Result: **serials 307–312 and 320–325 all stay silent.**

### G3 — `if(I.ScheduleCG && I.ScheduleDCG)` suppresses 326
**Scenario (case `GA_noDCG_a6e_nonzero`):** `ScheduleCG.ShortTermCapGain.SaleOnOtherAssets.DeemedSTCGDeprAsset`
= 41700 with `ScheduleDCG` **deleted**. Rule 326 requires A6e to equal Sl.6 of Schedule DCG,
which is nil here. Result: **326 stays silent.** The mirror case (`GA_noCG`, ScheduleCG deleted
while DCG total = 41700) is also silent, which is the correct half of the conjunction — with no
Schedule CG there is no A6e to check.

**Note on intent.** The batch header in `61_rules_enc_07.js` states the design deliberately:
"Every cond is TRUE when the data is absent or the schedule is not built." So G1–G3 are a
conscious choice, not an oversight, and the Yukti engine itself can never emit a DEP/DCG block
without its DPM/DOA source. The exposure is confined to imported JSON (Import / portal
pre-fill), where the guard is the only thing standing between a stripped schedule and a
silent upload. Nothing else in rules.json mandates DPM/DOA presence when DEP/DCG is filled
(checked: no serial in the whole file requires it), so there is no second line of defence.

## Other things worth the CEO's eye (not failures)

1. **327 and 329–337 are jointly restrictive, faithfully so.** Rule 327 lets ESR col (4) be
   positive (the sheet formula is `MAX(0, col3 − col2)`, and 328 totals it). Rules 329–337
   require col (3) = col (2) per row, which forces col (4) to zero. So a genuine weighted
   deduction — e.g. 35(2AB) in-house R&D where allowable exceeds the amount debited — passes 327
   but trips a Category-A block on 335. Verified: `L327_excess_positive_329fires` (debited
   100000, allowable 150000, excess 50000) → 327 silent, **329 fires**. The encoding reproduces
   rules.json exactly; the tension is the department's, not the form's. Flagging it because it
   means `TotUs35 ExcessAmtOverDebPL > 0` is effectively unreachable without a Category-A block,
   which will surprise a filer with a legitimate s.35(2AB) claim.
2. **302 encodes 1e, not the "1d" in the rules.json text.** rules.json 302 reads
   "6 Total depreciation should be equal to the sum of (1d + 2d + 3 + 4 + 5)". The encoding uses
   1e (`TotPlntMach`), matching sheet formula `[J18] = MAX(0, J9 + SUM(J14:J17))` where J9 = 1e.
   The batch comment already calls this out. Confirmed correct against `books/ITR-5/DEP_DCG.md`;
   the rules.json text is the typo. No action.
3. **315 is correctly signed where 302 is floored.** DEP total 6 is `MAX(0, …)`; DCG total 6 is
   not, because a deemed s.50 computation may be a loss (DCG cells carry min −99999999999999).
   Verified both ways: `L315_negative_total` (DCG 1e = −50000, total = −50000) is silent, and
   `V315_negative_total_floored` (same components, total wrongly floored to 0) **fires 315**.
4. **350 handles both the loss pass-through and the zero floor.** `A1e = (A1c < 0 ? A1c :
   MAX(0, A1c − A1d))`. Verified: balance −1,175,000 with A1e = −1,175,000 → silent, with
   A1e = 0 → **fires** (`V350_loss_not_passed`); balance 825,000 with a s.54 exemption of
   900,000 and A1e = 0 → silent, with A1e = −75,000 → **fires**.
5. **348–350 fire per A1 property row.** A second A1 property whose bv total (1,500,000)
   disagreed with bi+bii+biii+biv (1,000,000) fired 348 while row 0 stayed lawful
   (`V348_second_property`), so the `.forEach` is not short-circuiting on the first row.
6. **Documentation nit (no code impact).** `books/ITR-5/DEP_DCG.md` annotates the DEP/DCG
   totals with rules.json serials that are shifted by +2 — it cites "#303 DEP 1e", "#304 DEP 2d",
   "#305 DEP 6 total" where rules.json actually has 300, 301, 302 (303 is "DEP 1a = DPM 17i/18i").
   The **encoding follows rules.json and is correct**; only the book's cross-reference numbers
   are off. Worth a fix so a later reader does not "correct" the code to match the book.
