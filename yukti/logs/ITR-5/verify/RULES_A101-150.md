# ITR-5 · rule-firing verification — Category-A serials 101-150

Range: `books/ITR-5/rules.json` Category-A serials **101-150**
(Part A - Trading Account 101-107, Part A - P&L Account 108-150).
Encoded in `forms/ITR-5/src/61_rules_enc_03.js` (one `ruleset()` batch, registered as
`_RULEBATCHES[2]`); driven by `runRules()` in `forms/ITR-5/src/60_rules.js`.

Method: `forms/ITR-5/Yukti_ITR5.html` loaded in Chromium, `tests/ITR-5/state.js` injected,
`paint()`, then `BASE = Object.values(buildReturn().ITR)[0]` captured as the lawful reference
return (resident firm, OLD regime, full accounts case). Every scenario is a deep clone of that
engine-produced return, mutated at the key **the engine itself writes**, then passed to
`runRules(craftedReturn, S)`. Mutating the engine's own key (rather than the key the rule reads)
is what makes a wrong path in a rule visible: if the rule read a different key it would stay
silent on the mutation.

For every arithmetic rule the total was perturbed **and each component of the engine's own
formula was perturbed one at a time** with the total left untouched, so a component missing from
a rule's sum would show up as a non-firing case. 300 scenarios in all, plus 11 guard-side /
presumptive-lawful scenarios and 22 malformed-shape probes.

Baseline check: **the lawful reference return fires nothing at all** — `runRules` returns `[]`,
so no rule in this range false-fires on the reference client. Four further lawful returns
(44AD-only, 44ADA-only, 44AE-only, no-books-of-account) were built by stripping the accounts
blocks; none of them fires anything in 101-150 either.

Harness/evidence: `/tmp/claude-0/-home-user-CA-studio-/f83992ce-d154-5ec6-8aad-e2bd28be6369/scratchpad/rv/`
(`cases.py`, `runner.py`, `results.json`, `phase2.py`..`phase5.py`). Read-only run — no file under
`forms/` or `books/` was touched.

## FAILs

**Every FAIL below is a rule that stays SILENT on a return that violates it.** None of the 50 is a
false-fire. All five are the same defect: the rule is wrapped in a presence guard on the *other*
block of the cross-check, so deleting that block deletes the check instead of failing it. The
engine never emits such a return — these are exactly the hand-edited / portal-supplied returns
the brief points at.

**FAIL — serial 104 — `Trading item 11 = Manufacturing item 3` does not fire when the
Manufacturing Account is absent.**
`61_rules_enc_03.js`: `if(I.ManufacturingAccount) A(104, REQ(g(T,"GoodsCostPrdcdFrmMA"), g(M,"CostOfGoodsPrdcd")), …)`.
Scenario `guard-104-noMFG`: take the lawful return, keep `TradingAccount.GoodsCostPrdcdFrmMA = 4,400,000`,
delete the whole `ManufacturingAccount` block. Manufacturing item 3 is then nil, so item 11 must be
nil — the return violates serial 104. `runRules` returns nothing for 104.
(With the block present the rule fires correctly both ways: `104-mismatch` item 11 = 4,500,000 vs
item 3 = 4,400,000, and `104-mfg` item 3 moved to 4,500,000 with item 11 left behind.)
Fix direction: drop the guard and let the missing block read as 0 — `A(104, REQ(g(T,"GoodsCostPrdcdFrmMA"), g(M,"CostOfGoodsPrdcd")), …)`
unguarded already gives the right answer, because `RG`/`N` default the absent Manufacturing item 3 to 0.

**FAIL — serial 108 — `P&L item 13 = Trading 12 + 12b + 12d` does not fire when the Trading
Account is absent.**
`if(I.TradingAccount) A(108, …)`. Scenario `guard-108-noTA`: lawful return, `PARTA_PL.CreditsToPL.GrossProfitTrnsfFrmTrdAcc`
left at 5,700,000 (or any non-nil figure), `TradingAccount` deleted. Trading 12/12b/12d are then nil,
so item 13 must be nil; the rule is silent. Same fix: the rule is correct unguarded, since the
absent Trading Account defaults to 0.

**FAIL — serials 142, 143, 144 — the Schedule-BP A35 feeds do not fire when `CorpScheduleBP` is absent.**
All three read `if(I.CorpScheduleBP && I.PARTA_PL) A(n, REQ(BP A35(x), P&L 6x), …)`.
- `guard-142-noBP`: P&L 62ii = 100,000 (44AD business and code filled), `CorpScheduleBP` deleted — A35(i) is then nil against 62ii = 100,000, and serial 142 is silent.
- `guard-143-noBP`: P&L 63ii = 500,000, `CorpScheduleBP` deleted — serial 143 silent.
- `guard-144-noBP`: P&L 64iv = 90,000, `CorpScheduleBP` deleted — serial 144 silent.
Lower severity than 104/108, because `CorpScheduleBP` is a required schema block that the engine
always emits (`70_sec_bp.js`), so a return reaching this point without it would already fail the
shape audit. The guard is still the wrong shape: the `I.PARTA_PL` half is what makes the
comparison meaningful, the `I.CorpScheduleBP` half only removes the check.

## Defect that is not a single serial: one malformed array silences the rest of the batch

`60_rules.js` runs each batch inside one `try/catch` (`_RULEBATCHES.forEach(rb=>{try{rb(...)}catch(e){}})`),
and all fifty rules 101-150 live in a single batch. `RSUM(arr,"field")` (shell helper) and the
batch's own `has(a,k)` both throw on an array that is not an array, and `RSUM` also throws on an
array containing a `null` row. **A rule that throws aborts the rest of its batch silently** — every
serial after it in file order is simply never evaluated, and `runRules` reports nothing about it.

Confirmed by planting violations of serials 105, 111, 121, 123, 146, 147, 148 and 149 at once
(control fires `102,105,111,121,123,125,139,140,144,146,147,148,149`) and then adding one
malformed value:

| malformed value (hand-edited / portal-supplied return) | throws at | serials silenced |
|---|---|---|
| `PARTA_PL.CreditsToPL.OthIncome.OtherIncDtls` = a string | 109 | **109-150 (42 rules)** |
| `PARTA_PL.CreditsToPL.OthIncome.OtherIncDtls` = `[null]` | 109 | **109-150 (42 rules)** |
| `PARTA_PL.DebitsToPL.DebitPlAcnt.OtherExpensesDtls` = an object | 119 | **119-150 (32 rules)** |
| `PARTA_PL.DebitsToPL.DebitPlAcnt.OtherExpensesDtls` = `[null]` | 119 | **119-150 (32 rules)** |
| `PARTA_PL.NatOfBus44AD` = a string (with 44AD income declared) | 135 | **135-150 (16 rules)** |
| `PARTA_PL.GoodsDtlsUs44AE` = `[null, …]` | 146 | **146-150 (5 rules)** |
| `PARTA_PL.GoodsDtlsUs44AE` = a string or an object | 146 | **146-150 (5 rules)** |

`null` on its own is safe (`RSUM`'s `(arr||[])`), and `BadDebtAmtDtls` as a string is safe because
serial 120 reads the pre-totalled keys rather than summing the array. Serials 149 and 150 already
guard their rows with `if(!r) return;` — 146 does not.
Fix direction: make `RSUM` (and `has`) array-safe and null-row-safe, or wrap each `A(...)` rather
than each batch. The batch header comment claims "nothing throws; a rule is a no-op when its data
is absent" — that holds for absent data but not for wrong-typed data.

## Deviation to confirm — serial 141

Rule text: *"In Profit & Loss A/c, sl no 63i cannot be more than 63ii"*. Encoded the other way round,
as `63ii <= 63i`, with the reason written into the source. The literal reading cannot be right:
serial 134 requires 63ii >= 50% of 63i, so a lawful 44ADA return normally has 63i > 63ii, and the
literal check would fire on every one of them. Verified both readings:
- `141-over` (63ii = 1,200,000 against 63i = 1,000,000) — fires. Correct.
- `141-lawful` (63ii = 500,000 against 63i = 1,000,000, the ordinary 50% case) — silent under the
  encoded reading; the literal reading would have fired here. `141-equal` (63ii = 63i) — silent.
Flagged for the CEO because it is a deliberate departure from the text, not because it is wrong.

## Smaller notes (no FAIL, worth a line)

- **112** compares `AnyCompPaidToNonRes !== "Yes"` exactly. The form's enum is `Yes`/`No`
  (`PL_YN`), so engine returns are fine, but a hand-edited `"yes"` escapes the check
  (probe `lowerYes`: silent). Same shape as other enum comparisons in the batch.
- **124** is silent when `PartA_GEN1.OrgFirmInfo.StatusOrCompanyType` is absent (probe `noStatus`).
  Defensible — absence is not proof of a non-Firm status — but it is worth knowing.
  The status codes are right: `GEN_STATUS` in `70_sec_gen.js` is `1 = Firm`, `2 = Local Authority`,
  `9 = Artificial Juridical Person`, `14 = AOP/BOI`, and the rule excludes exactly 2/9/14, so a
  Firm claiming item 46 stays silent (`124-firm`) while AOP/BOI, Local Authority and AJP all fire.
- **150** skips a carriage whose `TonnageCapacity` is 0 (the rule requires `>0 && <=12`), so a row
  with a blank tonnage and nil income passes (probe `tonnageZero`). The >12 MT limb is serial 151,
  outside this range.
- **103** only skips negatives by *key name* (`GoodsCostPrdcdFrmMA`, `GrossProfitFrmBusProf`,
  `IntradayTradingIncome`, `IncomeFutureTrd`) rather than by path, but no other key in the Trading
  Account block shares those names, so it is exact in practice. Verified: negative Purchases,
  negative closing stock and a negative row in the 9iii table all fire; negative item 11 and
  negative item 12 stay silent, as the text requires.
- **147** is guarded by `if(goods.length)`, which is correct — with no 64i table there are no months
  to total. Boundary verified at exactly 120 months (silent) and 121 (fires).
- **148** encodes `MAX(0, 64ii - 64iii)`, matching the engine; verified that 64iii > 64ii leaves
  64iv nil without firing.
