# ITR-5 · AY 2026-27 — rule firing verification, Category-A serials 51–100

**Question answered:** for every rule in this range, does the encoded check *fire* on a return that
violates it, and stay *silent* on a lawful one, in the direction the rule's own text states?

**Encoding under test:** `forms/ITR-5/src/61_rules_enc_02.js` (assembled into
`forms/ITR-5/Yukti_ITR5.html`, batch `enc_02`). Form and books read-only; nothing was edited.

**Method**
* Playwright + Chromium, `file://forms/ITR-5/Yukti_ITR5.html`, state injected, `paint()`, then
  `runRules(Object.values(buildReturn().ITR)[0], S)` (pattern of `tools/harness/run_form.py`).
* Lawful reference client: `tests/ITR-5/state.js` (S SUDHIR AND ASSOCIATES, resident partnership
  firm, OLD regime, 44AB audit, BS + P&L + Manufacturing + Trading all populated).
  **Baseline: `runRules` returns zero Category-A and zero Category-D items — no rule in 51–100
  fires on the lawful reference return.**
* **156 crafted-return cases** (deep clone of the built return, one targeted mutation each, then
  `runRules(craftedReturn, S)`) — 63 violation cases and 93 lawful cases. Every conditional rule was
  driven on **both sides of its guard** (guard on + violating, guard on + compliant, guard off).
* **21 engine-driven scenarios** — real state variants painted through the form and exported by
  `buildReturn()`, used to confirm that the crafted findings are reachable from the actual UI and
  not artefacts of hand-editing.
* **18 edge probes** — REQ tolerance boundary, empty-string vs absent leaves, foreign secondary
  address, schedule-presence guards, and a rig negative control.

Result files (scratchpad): `rv_a051/results_a051.json`, `rv/engine.json`, `rv/engine2.json`.

## FAILURES

### **FAIL-1 — serial 51 false-fires on a lawful old-regime return carried over from an earlier AY**

Rule text: *"New tax regime can be Opted out or withdrawn only if Form 10IEA is filed."*

Encoding (`61_rules_enc_02.js`):

```js
A(51,FS.OptOldRegimeCurrAY!=="Y"||!hasBP||FS.F10IEACurrAYOldRegime==="Y", …)
```

The only accepted proof that Form 10-IEA was filed is the **current-AY** answer
`F10IEACurrAYOldRegime === "Y"`. The **earlier-AY** arm of the same A19 d(i) tree —
`Form10IEAEarlierAYOldRegime` (+ `Form10IEAEarlierAYAckOldRegime`, `Form10IEAAssYear`) — is not
accepted. Under s.115BAC(6) the opt-out is exercised once and continues for later years, so a firm
that filed Form 10-IEA for AY 2024-25 and stays in the old regime for AY 2026-27 answers the
current-AY question "No" and the earlier-AY question "Yes". That is exactly the lawful case the
earlier-AY fields exist for, and rule 51 blocks it.

**Exact scenario (engine-driven, scenario G1 — reproduces from the real UI, not hand-edited):**

```
tests/ITR-5/state.js  +
  S.fs.f10ieaCurrOld     = "N";   delete S.fs.f10ieaDateOld; delete S.fs.f10ieaAckOld;
  S.fs.f10ieaEarlierOld  = "Y";
  S.fs.f10ieaEarlierAckOld = "777888999000111";
  S.fs.f10ieaEarlierAY   = "2024";
```

Built return carries `OptOldRegimeCurrAY=Y`, `F10IEACurrAYOldRegime=N`,
`Form10IEAEarlierAYOldRegime=Y`, `Form10IEAEarlierAYAckOldRegime=777888999000111`,
`Form10IEAAssYear=2024`.
`runRules` → **`A(51)` fires**: *"the new tax regime can be opted out / withdrawn only if Form
10-IEA is filed for the current AY."* Nothing else fires. The return is lawful and complete.

Sanity check that the rule is otherwise sound: with the current-AY answer absent altogether
(scenario G2) serials 51 **and** 68 fire, and 68 is correct there. The fix belongs only in 51:
the earlier-AY branch must also satisfy it (`|| FS.Form10IEAEarlierAYOldRegime === "Y"`), which is
how serial 75 in the same batch already treats the four 10-IEA branches.

### **FAIL-2 — serial 56 false-fires when the 31-October due date rests on an audit under another law**

Rule text: *"If Due date 31st October is selected, kindly fill Schedule IF or Schedule 5A or audit
details in Part A Gen."*

Encoding:

```js
A(56,due!=="2026-10-31"||FS.PartnerInFirmFlg==="Y"||G2.LiableSec44ABflg==="Y"
     ||G2.LiableSec92Eflg==="Y"||G2.AuditedByAccountantFlg==="Y", …)
```

"Audit details in Part A Gen" is read as *44AB or 92E only*. Part A-General 2 also carries
**`PartA_GEN2.AuditDetails`** (other audit reports under the Income-tax Act, item d(iii)) and
**`PartA_GEN2.AuditReportDetails`** (audits under an Act *other than* the Income-tax Act, item e) —
neither is consulted. A 31-Oct due date is correct under s.139(1) Expl. 2(a)(ii) for any person
whose accounts must be audited *"under this Act or under any other law"*, e.g. a co-operative
society audited under a State Co-operative Societies Act and not liable u/s 44AB.

**Exact scenario (engine-driven, scenario F1):**

```
tests/ITR-5/state.js  +
  S.aud.sec44AB="N"; S.aud.acctFlg="N"; S.aud.sec92E="N";
  S.aud.pctRcvd="Upto5Per"; S.aud.pctPaid="Upto5Per";
  S.fs.partner="N"; S.other.if={n:"",firms:[]};
  S.fs.duedate="2026-10-31";
  S.aud.act=[{act:"Co-operative Societies Act, 1959",section:"64",flag:"Y",date:"20/09/2026"}];
```

Built return has `LiableSec44ABflg=N`, `LiableSec92Eflg=N`, one `AuditReportDetails` row (other Act)
and one `AuditDetails` row (other IT-Act section).
`runRules` → **`A(56)` fires** and is the only Category-A item. Audit details *are* filled in
Part A General; the rule's own condition is satisfied.

Two further defects in the same guard:

1. **`AuditedByAccountantFlg` is a dead arm.** `70_sec_gen.js` writes it only inside
   `if(S.aud.sec44AB==="Y")`, so it can never be `"Y"` while `LiableSec44ABflg` is not `"Y"`. The
   third escape hatch adds nothing.
2. **Schedule IF is tested by proxy.** The guard reads `FS.PartnerInFirmFlg`, not `I.ScheduleIF`.
   `ScheduleIF` is built from `S.other.if` independently of `S.fs.partner`
   (`70_sec_other.js` ~line 397), so a return can carry a fully populated Schedule IF while the
   flag is `"N"` — verified in engine scenario E2 (`hasIF = true`, `PartnerInFirmFlg = N`,
   `A(56)` fires). No other rule cross-checks the two, so nothing else catches the inconsistency.

## Encoding gaps found while testing (not firing failures, but the CEO should see them)

### **GAP-1 — serials 53 and 54 are not encoded, and the recorded reason is factually wrong**

`61_rules_enc_02.js` declares:

> `/* 53 — NOT MAPPABLE: … The 115BAE d(iv) sub-fields are on hidden rows and are not built in this form (PART_A_GENERAL.md §9). */`
> `/* 54 — NOT MAPPABLE: … Same reason as 53 — not built. */`

They **are** built. `70_sec_gen.js` renders the d(iv) block (lines 277–284) and emits
(lines 552–554):

* `PartA_GEN1.FilingStatus.115BAEReturnFiling_24_25` — d(iv), "were you required to furnish the
  return for AY 2024-25 / 2025-26?"
* `PartA_GEN1.FilingStatus.OptingTaxation115BAEYes` — d(iv)(a)
* `PartA_GEN1.FilingStatus.OptingTaxation115BAENo` — d(iv)(b)

`PART_A_GENERAL.md` documents all three (rows F85 / F92 / F96), and serials 44 and 48 in `enc_01`
already read `OptingTaxation115BAEYes` / `Form10IFADate`, so the leaves are demonstrably live.

Verified by engine scenario (co-operative society, `tests/ITR-5/verify/sc_coop.js`):

| scenario | built leaves | rules fired |
|---|---|---|
| K1: `S.fs.baeReturn="N"`, `S.fs.baeNo` deleted (d(iv) = No, option at d(iv)(b) left blank) | `115BAEReturnFiling_24_25=N`; `OptingTaxation115BAENo` **absent** | none |
| K2: `S.fs.baeReturn="Y"`, `S.fs.baeYes` deleted (d(iv) = Yes, option at d(iv)(a) left blank) | `115BAEReturnFiling_24_25=Y`; `OptingTaxation115BAEYes` **absent** | none |

Both are precisely the violations serials 53 and 54 describe, and the form is silent on both. These
two rules are offline-checkable with the leaves already in the schema and should be encoded.

Related: `logs/ITR-5/rule_audit/census/CENSUS_A_1-347.md` is also wrong here — its rows for
Category-A 53 and 54 carry 80G-donee-PAN and nature-of-business-code justifications that belong to
other serials, and its row for Category-A 55 cites `enc_22`, which actually registers `Dd(55, …)`,
a **Category-B** serial. The census claim of "0 offline-checkable rules missing" does not hold for
this slice.

### **GAP-2 — serial 55 may be encodable after all**

The `/* 55 — NOT MAPPABLE */` note says there is no filing-date leaf in the return schema. True of
the return, but `runRules(I, S_)` also receives the whole state, and the form *does* capture the
filing date: `S.fs.filed` ("Date of filing the return", `70_sec_tax.js` line 435, already used for
the 234A/234F computation at line 272). "Return cannot be submitted u/s 139(1) after the due date"
is `S_.fs.sec === 11 && D(S_.fs.filed) > S_.fs.duedate`. Flagging for the CEO's judgement — not
counted as a failure, since the rule is honestly declared unencoded.

## Notes (verified behaviour, no action strictly required)

* **NOTE-1 — serial 65 is correct but unreachable from the UI.** Its premise is *new regime +
  business income + `Form10IEAEarlierAYOldRegime === "Y"` + no earlier re-entry*. `70_sec_gen.js`
  writes `Form10IEAEarlierAYOldRegime` only inside `if(old)`, so the new-regime branch drops the
  field. Engine scenario H1 (`S.fs.optout="No"` with `S.fs.f10ieaEarlierOld="Y"`) produces a return
  with **no** 10-IEA leaves at all and fires nothing. The rule fires correctly on a crafted /
  portal-supplied return (verified), so it is a live guard against an imported return — but as a
  UI-side check it is dead. If the earlier-AY old-regime question is meant to be visible to
  new-regime filers (it is, in the department's own A19 d(i) tree), the builder needs to emit it
  outside the `if(old)` branch.
* **NOTE-2 — serials 61 and 62 can only ever fire on a crafted / imported return.** The builder
  always writes `OptOldRegimeCurrAY` as `"Y"`/`"N"`, and both rules sit inside `if(I.PartA_GEN1)`.
  Both fire correctly when the leaf is removed, and both stay silent when `PartA_GEN1` is absent
  altogether (probe verified). This is the intended shape of a presence guard, recorded for clarity.
* **NOTE-3 — serial 74 can be evaded with a junk field.** The comparison is
  `K.some(k => String(AA[k]) !== String(PA[k]))` over nine address keys. A secondary address
  identical to the primary in all eight populated keys but carrying an extra `ZipCode` passes
  silently (probe verified). Not a false-fire; only an under-fire on a deliberately padded return.
* **REQ tolerance behaves as designed.** Every arithmetic rule (81–100) uses `REQ(a,b)` with the
  default ±1 tolerance: an off-by-1 return stays silent, an off-by-2 return fires (probe verified
  on serial 81). Correct for rupee-rounded schedules.
* **Schedule-presence guards are sound.** Serials 81–88 (`if(I.PARTA_BS)`), 89–95
  (`if(I.ManufacturingAccount)`) and 96–100 (`if(I.TradingAccount)`) all go silent when their block
  is absent, even with the violating figures left in place — a presumptive or no-accounts filer is
  not nagged. 15 lawful cases confirm this.
* **Empty string vs absent leaf.** Serials 66/67/69/70/71/72 treat `""` as "not provided"
  (`!""` → true), so a blanked-out date or acknowledgement number is handled the same as a deleted
  one. Probe verified on 69 (fires) and 70 (stays silent).
* **Serial 95 catches a negative leaf even when the totals still reconcile** — verified with
  `OpngStckRawMat = -500000` / `OpngStckWrkinPrgrs = 1100000` (total unchanged at 600000) and again
  with a negative nested factory-overhead leaf.
