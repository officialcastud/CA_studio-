# ITR-5 · rule-firing verification — Category-A serials 151-200

**Range**: `books/ITR-5/rules.json` Category A, serials 151-200 (Part A-P&L 151-179, Part A-OI 180-191, Schedule HP 192-200).
**Encoding under test**: `forms/ITR-5/src/61_rules_enc_04.js`, assembled into `forms/ITR-5/Yukti_ITR5.html`
(batch located at runtime as `_RULEBATCHES[i]`; 24 batches registered, batch-04 found in every run).
**Method**: Playwright loads `forms/ITR-5/Yukti_ITR5.html`, injects `tests/ITR-5/state.js` (resident partnership
firm, OLD regime), `paint()`, then `buildReturn()` is snapshotted as the lawful reference return object.
Each scenario deep-clones that object, applies one mutation, and is run through **both**
`runRules(I,S)` **and** the isolated batch-04 function called with its own `A`/`Dd` collectors — the
isolated call is what proves a rule fired, because `runRules` swallows a throwing batch (see FAIL-1).
Crafted (non-engine-producible) returns were used wherever the rule exists to guard against a
hand-edited / portal-supplied return, as the brief permits.
**Nothing in `forms/` or `books/` was edited.**

**Volume**: 206 scenario runs (163 primary + 39 adversarial probes + 4 blast-radius controls) plus
63 lawful state files loaded end-to-end through the form, twice.
Harness + raw results: `/tmp/claude-0/-home-user-CA-studio-/f83992ce-d154-5ec6-8aad-e2bd28be6369/scratchpad/rv_a151_200/`
(`drive.py`, `gen*.py`, `scen*.json`, `res*.json`, `lawful*.json`).

## Verdict policy

* **fires-on-violation Y** — every violation scenario tested for that serial, in the direction the rule's
  own text states, produced the serial from the batch.
* **silent-on-lawful Y** — every lawful scenario tested for that serial (including the far side of each
  guard) produced nothing for that serial, and the serial never appears on the lawful reference return.
* **FAIL** — a violation of the rule's own text that the assembled form can put into a return (or that
  the rule was written specifically to catch) leaves the check silent, or the check fires on lawful data.
* Narrower blind spots that are only reachable by hand-editing a return are recorded as **gaps** (G1-G4)
  rather than FAIL, with the exact scenario, so they can be judged on their merits.

## FAILURES

### **FAIL-1 — cross-cutting: one non-array leaf silently kills the whole batch, taking all 50 rules (151-200) with it**

`61_rules_enc_04.js` reads nine array leaves through `RG(...,[])` / `(X||{})` and then calls
`.forEach` / `.filter` / `.map` / `.some` / `.every` / `RSUM` on the result. `RG` returns the **stored
value whenever it is non-null** — the `[]` default only applies when the path is missing — so a leaf
that arrives as an object, a string or a number is handed straight to an array method and throws.
`runRules` wraps each batch in `try{...}catch(e){}` (`forms/ITR-5/src/60_rules.js`), so the throw is
swallowed: the batch stops dead at that point and **every Category-A rule at or after it never runs**.
The file's own header claims "Every read is guarded (RG / (X||{})); nothing throws" — that claim does
not hold.

Exact scenario (control vs blast, all on the lawful reference return):

| scenario | mutation | batch-04 fires |
|---|---|---|
| control | HP `1e` = 600000 (should be 560000), HP `1g` = 1 (should be 168000), OI `5f` = 99999 (should be 0) | `[182, 192, 199]` — correct |
| blast-co | **the same three violations**, plus `ScheduleHP.PropertyDetails[0].CoOwners` supplied as `{"0":{...}}` instead of `[...]` | `[182]` — 192 and 199 lost; `TypeError: (arr \|\| []).reduce is not a function` |
| blast-bd | **the same three violations**, plus `...BadDebtDtls.BadDebtAmtDtls` supplied as `{"0":{...}}` | `[]` — **all three lost**; throw at serial 162 kills 162-200 *and* 182-191 |
| blast-null | HP `1e` and OI `5f` violations, plus `ScheduleHP.PropertyDetails` supplied as the string `"none"` | `[182]` — 192-200 lost; `TypeError: props.forEach is not a function` |

The nine vulnerable reads, with the throwing scenario id from `res2.json`:

| leaf | serials silenced from that point on | probe |
|---|---|---|
| `PARTA_PL.NatOfBus44AD` | 152-200 | `x-nob-obj` |
| `PARTA_PL.DebitsToPL.DebitPlAcnt.BadDebtDtls.BadDebtAmtDtls` | 162-200 | `x-bd-obj` |
| `PARTA_PL.GoodsDtlsUs44AE` | 163-200 | `x-ae-obj` |
| `PartA_GEN2.PartnerOrMemberInfo` (and `PrevYrMemPart.PrevYrMemPartDtls`) | 165-200 | `x-gen2-obj` |
| `PARTA_PL.DebitsToPL.DebitPlAcnt.BadDebtDtls.OthersPANNotAvlblDtl` | 172-200 | (same shape as `x-bd-obj`) |
| `PARTA_PL.NonResidentPLDetails` | 173-200 | `x-nr-obj` |
| `ScheduleHP.PropertyDetails` | 192-200 | `x-hp-obj`, `blast-null` |
| `ScheduleHP.PropertyDetails[].CoOwners` | 192-200 | `x-co-obj`, `blast-co` |

Not reachable from the form's own `buildReturn()` (it always emits arrays), but squarely inside the
population these rules exist for: an imported / portal-supplied / hand-edited return. A single
malformed leaf turns 50 blocking checks into silence with no visible error anywhere.

**The fix is already in the codebase**: batch `61_rules_enc_09.js` defines
`const AR=x=>Array.isArray(x)?x:[];` at the top of its `ruleset(...)` and routes every array read
through it. Batch 04 needs the same helper applied to the nine reads above.

### **FAIL-2 — serial 164 never fires for a no-account (Sl.No. 65) filer**

Rule text: *"If Sale / Gross receipts of Business are more than 10 crore or Gross receipts from
Profession are more than 50 Lakhs then assessee should be liable for audit u/s 44AB. So 'Whether
liable for audit under section 44AB?' should be 'Yes'."*

The encoding reads the turnover **only from the Trading Account** and is wrapped in `if(I.TradingAccount){...}`:

```js
if(I.TradingAccount){const trd=I.TradingAccount;
  A(164,!(N(trd.SalesGrossReceiptsTotal)>100000000||N(trd.GrossRcptFromProfession)>5000000)||aud44AB, ...);
}
```

A filer on the **no-account route** puts turnover at P&L Sl.No. 65(i)a / 65(ii)a
(`PARTA_PL.NoBooksOfAccPL.GrossReceipt` / `.GrossReceiptPrf`) and leaves the trading account blank.
`forms/ITR-5/src/70_sec_pl.js:602` emits the block only when it has content
(`if(_plHas(B.trd)) put(j,"TradingAccount",...)`), so there is **no `TradingAccount` key at all** and
the rule is skipped outright.

Exact scenario (`p164-nobooks`): on the lawful reference return, delete `TradingAccount`, set
`PARTA_PL.NoBooksOfAccPL.GrossReceipt` = `110000000` (Rs.11 crore) and
`.GrsRcptAccPayeeOrBankMode` = `110000000`, set `PartA_GEN2.LiableSec44ABflg` = `"N"`.
Result: batch-04 fires **nothing** — 164 is silent on an Rs.11-crore business declaring no tax audit.
The same hole exists for 65(ii)a profession receipts above Rs.50 lakh.

This one is producible by the assembled form itself, not only by a hand-edited return.
(Judgement call for the fix: the CBDT wording is P&L-wide, so 65(i)a / 65(ii)a should be folded into
the same comparison and the `if(I.TradingAccount)` wrapper dropped. The presumptive routes at 62i/63i
are already covered separately by serials 168-171.)

## Recorded gaps (fire correctly on every form-producible violation; blind on one narrower class)

**G1 — serial 198, `ifLetOut` leaf absent.** Guard is `(p.ifLetOut!=="Y"&&p.ifLetOut!=="D")`. The
engine always writes `Y` or `D` (`70_sec_hp.js:365`, and `enums.json` allows only those two), so this
is unreachable from the form; a hand-edited return that simply omits `ifLetOut` while carrying a zero
`AnnualLetableValue` escapes the check. Probe `p198-noflag`: batch fired `[199]` only, not 198.

**G2 — serial 190, present-but-empty Schedule TPSA.** The condition is `!!I.ScheduleTPSA`, so an
empty object `{}` satisfies "Schedule TPSA should be filled". Probe `p190-empty`: silent. Not
form-producible (`70_sec_other.js:443` always writes populated leaves when the flag is `Yes`).

**G3 — serial 190, flag case.** The condition is `oi.ScheduleTPSAFlg!=="Yes"`. `ScheduleTPSAFlg` is a
free string in the schema (it is *not* in `books/ITR-5/enums.json`; `70_sec_oi.js:58-61` records the
dropdown literally as `Yes`/`No`), so a portal return spelling it `"YES"` bypasses the rule entirely.
Probe `p190-case`: silent.

**G4 — serials 180 / 181, the zero-value gate.** Both rules are wrapped in
`if(I.ScheduleICDS && N(oi.<cell>))`, so they fire on a *wrong non-zero* OI 3a/3b but are silent when
the cell is zeroed while Schedule ICDS carries a non-zero XI(3)/XI(4) — i.e. exactly the
under-reporting direction. Probes `180L-zero` (3a = 0 vs ICDS XI(3) = 25000) and `181L-zero`
(3b = 0 vs ICDS XI(4) = 7000): both silent.
This narrowing is **deliberate** and documented in the encoding ("checked only when 3a is itself
populated … an engine-seam gap, not a lawful-data violation"): OI 3a/3b are read-only cells fed from
Schedule ICDS across a cross-section seam, and removing the guard would make the rule false-fire
wherever the seam has not yet fed the cell. Flagged for a decision, not filed as a FAIL — the safe
fix is to close the seam (always feed 3a/3b from ICDS) and only then drop the value gate.

### Note on serial 165 and the `re_*` chassis (not a rule defect)

On a first sweep, serial 165 fired on 53 of the 63 lawful state files. Cause: the `re_*.js` chassis
files replace `S.pm` (partners/members, set to `members:[]`) but **do not reset `S.pl`**, so when they
are layered on `tests/ITR-5/state.js` — the layering `tests/ITR-5/verify/caps_drive.py` also uses —
the baseline P&L keeps `SalRemuneration` = 800000 while Part A General-2 reports no partner
remuneration at all. Serial 165 is **correct** to fire on that: the return genuinely disagrees with
itself. Re-running the whole sweep with the artefact removed (zeroing P&L 46 when the member table is
empty) drops it to 2 of 63, and both survivors are the same artefact in a different shape:
`re_f1_aop_member_exceeds.js` and `re_f2_aop_foreign_member.js` declare members with **no `remun`
key**, so Part A General-2 reports Rs.0 of remuneration while the inherited P&L still carries
`SalRemuneration` = 800000. Zeroing P&L 46 in those two runs takes the sweep to **63 of 63 clean**
(`lawful3.py`: `{'inrange': [], 'pl46': 0, 'gen2rem': 0}` for both). All ten `sc_*.js` states, which
layer on the complete reference state, were clean on every sweep.

Two follow-ups for whoever owns those files (outside this range, flagged only because the sweep
surfaced them): the `re_*.js` chassis should reset `S.pl` (and `S.bs`) alongside `S.pm`, otherwise every
case built on it carries a return that disagrees with itself at P&L 46; and `tests/ITR-5/verify/caps_drive.py`
layers the same way, so its cases inherit the same inconsistency.

## Bottom line

Of the 50 encoded rules in this range, **49 fire on violation and are silent on lawful data in the
direction their own text states**. Serial 164 misses the no-account route outright (FAIL-2). Separately,
a single unguarded array read anywhere in the batch can silence all 50 at once on an imported or
hand-edited return (FAIL-1) — the highest-value fix in this range, and a one-line helper the codebase
already uses elsewhere. Four rules (180, 181, 190, 198) carry narrower blind spots recorded as G1-G4.
No rule in the range false-fires.
