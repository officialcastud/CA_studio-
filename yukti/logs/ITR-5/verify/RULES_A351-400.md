# ITR-5 · rule-firing verification — Category-A serials 351-400 (Schedule CG)

**Question answered:** for each encoded rule in this range, does the check actually *fire* on a
return that violates it, and stay *silent* on a lawful one, in the direction the rule's own text states?

**Under test:** `forms/ITR-5/Yukti_ITR5.html` (assembled 22 Sep 2026), rules batch
`forms/ITR-5/src/61_rules_enc_08.js` — the whole of serials 351-400 lives in that one file.
Serials come from `books/ITR-5/rules.json`. Nothing in `forms/` or `books/` was edited.

**Method.** Playwright (pattern `tools/harness/run_form.py`): load the form, inject a state,
`paint()`, then read `runRules(Object.values(buildReturn().ITR)[0], S)`. Two complementary passes:

1. **Engine-driven lawful pass** — four states injected on top of `tests/ITR-5/state.js`
   (the lawful resident firm, OLD regime) that turn *every* Schedule-CG head in this range on and
   let the engine compute the figures itself. This is the only honest test of "silent on a lawful
   return": the figures are the engine's, not the rule's own formula echoed back.
   - `cg_res` — resident: A2 slump, A3 (both sub-heads, one of them a loss), A6, A7 (unutilised
     CGAS + 7b + 7c), A8, B1 LTCG land with a 54EC claim, B2 slump with 54EC, B3, B4, B8 with a
     54D claim, B9, B10, Table D (54D + 54EC), a live Table-E set-off, Table F vs BFLA.
   - `cg_nri` — non-resident / FII: A4, A5 (115AD), A9 DTAA, B5, B6, B7 + Schedule 115AD, B11 DTAA.
   - `cg_all` — both at once.
   - `cg_loss` — applicable-rate STCG bucket driven to a net loss (for the Table-E floor).
2. **Crafted-violation pass** — 94 cases (53 violation, 23 lawful-populated, 18 guard). The lawful engine return is deep-cloned, one leaf is
   moved off its identity (compensating the downstream leaves so that, wherever possible, **exactly
   one** serial fires), and `runRules(craftedReturn, S)` is called. This is the right tool here:
   every rule in this range is an arithmetic identity the engine itself can never break, so the
   violation can only come from a hand-edited or portal-supplied return.
   Both sides of every guard were tested (head present / head absent).

Harness and scenario files: `scratchpad/verify_351_400.py`, `scratchpad/drive_scenarios.py`,
`scratchpad/sc/cg_{res,nri,all,loss}.js`.

## 3 · The four un-encoded serials (389, 390, 393, 394) — verified as correctly left out

`61_rules_enc_08.js` leaves these four deliberately un-encoded, with a comment at the foot of the
batch, and `logs/ITR-5/rule_audit/census/CENSUS_A_348-611.md` buckets them OFFLINE-IMPOSSIBLE.
I checked that justification against the engine rather than taking it on trust, and it holds:

- **389 / 393 (Ei3 / Eiii — the 30 % income row).** The rule text says the row equals
  `A5e + A8b + A(A)@30%`. It omits A3iie, which the ITR-5 engine puts in the same bucket
  (`70_sec_cg.js` Table-E composition: `30% = A3iie + A5e + A8b − STL30`). On the lawful
  `cg_res` return the engine's row is **2,10,000** (A3iie 1,90,000 + A8b 20,000) while the rule's
  literal right-hand side is **20,000**. A faithful encoding would fire on a lawful return.
- **390 / 394 (Ei4 / Eiv — the applicable-rate income row).** The row is written
  `n0(G.gain.stApp)` — floored at zero — while the rule's literal sum is not. On the `cg_loss`
  return the engine's row is **0** and the literal sum `A1e + A6g` is **−41,00,000**
  (the loss is carried in `InLossSetOff.StclSetoffAppRate = 41,00,000` instead). Again a faithful
  encoding would fire on a lawful return.

Both rule texts are also truncated across serial boundaries in `rules.json` (the "as reduced by the
amount of STCG chargeable … at special rates in A9a & A9b" clause runs from 389 into 390 and from
393 into 394), and the ITR-5 build never nets DTAA gains out of the 30 %/applicable-rate rows —
it routes them into their own `InStcgDTAARate` bucket — so the reduction clause has no leaf to test.
**Nothing to fix. These four are correctly un-encoded, for the reason the batch states.**

## 4 · **GUARD GAPS — rules that stay silent on a return that does violate their text**

None of these is an arithmetic error; each is a **conditional guard placed on only one side of a
cross-node comparison**. The engine always emits both nodes, so none is reachable from the form
itself — but each is reachable from a hand-edited or portal-supplied return, which is exactly what a
Category-A upload check exists to stop. Listed worst first.

**1. Serial 373 — B4 vs Schedule 112A. Guard is on the right-hand side only.**
`if(I.Schedule112A)` gates the check, but `LT.SaleOfEquityShareUs112A` is emitted unconditionally.
*Exact scenario tested:* `SaleOfEquityShareUs112A.CapgainonAssets = 6,00,000`, `Schedule112A`
deleted from the return. Col-14 total is then nil, so B4 ≠ the total and the rule is violated —
**runRules returns nothing.** (With both nodes present it fires correctly, both directions.)

**2. Serial 378 — B7 vs Schedule 115AD. Same shape.**
`if(I.Schedule115AD)` gates the check; `LT.NRISaleOfEquityShareUs112A` is emitted for any NR/FII.
*Exact scenario tested:* `NRISaleOfEquityShareUs112A.CapgainonAssets = 4,00,000`, `Schedule115AD`
deleted — **silent.**

**3. Serials 391 / 395 — Ei5 (Ev) vs A9b.** Guard `if(CYL.InStcgDTAARate)`.
*Exact scenario tested:* `ScheduleCG.CurrYrLosses.InStcgDTAARate` deleted while
`ShortTermCapGain.TotalAmtTaxUsDTAAStcg = 2,50,000` — the row is absent (i.e. nil) against a
non-nil A9b, and **neither serial fires.**

**4. Serials 392 / 396 — Ei7 (Evii) vs B11b.** Guard `if(CYL.InLtcgDTAARate)`.
*Exact scenario tested:* `InLtcgDTAARate` deleted while `TotalAmtTaxUsDTAALtcg = 3,00,000` — **silent.**

**5. Serials 399 / 400 — Table F vs Schedule BFLA.** Guard `if(AF && I.ScheduleBFLA)`.
*Exact scenarios tested:* (a) `ScheduleBFLA` deleted while Table F Sl.2 shows 1,00,000 — **silent**;
(b) `ScheduleCG.AccruOrRecOfCG` deleted while BFLA 5viii = 8,00,000 — **silent**.

**6. Serials 387 / 388 — Table E totals.** Guard
`if(CYL.TotLossSetOff && CYL.InLossSetOff && CYL.LossRemainSetOff)`.
*Exact scenario tested:* `TotLossSetOff` deleted while `LossRemainSetOff.StclSetoff30Per = 50,000`
and `InLossSetOff.StclSetoff30Per = 2,00,000` — Eix should then be 2,00,000, so the return is
inconsistent, and **neither serial fires.**

**7. Serial 398 — Table E col-8.** Per-row guard `if(!node) return`.
*Exact scenario tested:* all six income rows deleted — **silent** (arguably correct: with no rows
there is nothing to check; noted for completeness).

**8. The whole batch — `if(!CG || typeof CG !== "object") return;`.**
*Exact scenario tested:* `ScheduleCG` deleted while a broken A2c is carried in the state —
**the entire 50-serial batch is silent.** This is the batch's documented convention and matches
every other enc_ file, but it means a return that drops Schedule CG while Part B-TI still reports
capital gains is not caught anywhere in this range.

Guards verified **correct** (the gated node holds *both* sides of the comparison, so an absent node
leaves nothing to violate): 351, 352-354, 355-359, 360-363, 366-368, 369-370, 371-372, 374-377,
379-383.

## 6 · Verdict for this range

**Every encoded rule in Category-A 351-400 bites.** 46 of 46 fire on a violation in the direction
their text states and are silent on a lawful return — confirmed against the engine's own output
with every Schedule-CG head in the range live, resident and non-resident. Zero arithmetic FAILs.
The four un-encoded serials (389, 390, 393, 394) are correctly un-encoded, and I verified the
stated reason rather than accepting it. The only defect class found is the eleven **guard gaps** in
§4, all of the same shape — a conditional placed on one side of a cross-node comparison — of which
**373 and 378 are the two worth fixing first**, because there the gated node (a scrip schedule) can
plausibly be missing from a supplied return while the node it is compared against is always present.

Report only; the form was not edited.
