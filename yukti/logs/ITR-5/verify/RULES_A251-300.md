# ITR-5 · A.Y. 2026-27 — rule-firing verification, Category-A serials 251-300

**Question answered:** for every encoded rule in this range, does it actually *fire* on a return
that violates it, and stay *silent* on a lawful one, in the direction the rule's own text states?

**Method.** The assembled form (`forms/ITR-5/Yukti_ITR5.html`) was driven with Playwright
(pattern of `tools/harness/run_form.py`). The lawful reference client `tests/ITR-5/state.js`
(resident partnership firm, OLD regime) was injected and `paint()` run; the built return
`Object.values(buildReturn().ITR)[0]` became the baseline. Each case deep-clones that baseline,
applies a small set of path mutations, and calls `runRules(clone, S)`. Depreciation-block
violations were crafted as *fully self-consistent* blocks (built from the sheet formulas in
`books/ITR-5/DPM_DOA.md`) with exactly one item perturbed, so the target rule fires alone
wherever the schedule's own arithmetic allows it. Crafted returns are the right instrument here:
these rules guard against a hand-edited or portal-supplied return that the engine itself would
never emit.

**Baseline control: `runRules` on the untouched lawful reference return fires 0 rules** (Category A
and Category D both empty), with no page errors. Every "silent-on-lawful" verdict below is measured
against a return that is lawful *in the respect the rule tests*.

**Volume.** 165 crafted cases (violation + lawful + guard-branch per serial) plus all 53
engine-produced entity/regime scenarios in `tests/ITR-5/verify/re_*.js` re-run end-to-end.

### Value-conditional guards inside the depreciation blocks
* `deemed > 0` floor (285 DPM / 296 DOA): fires when the consideration exceeds opening WDV +
  additions and Sl.20/Sl.17 falls short; skipped (silent) when consideration does not exceed it.
* `Sl.20 ≠ 0` / `Sl.17 ≠ 0` ceased-block consequences (286 / 297): fire when any of Sl.10-18/21
  (DPM) or Sl.10-15/18 (DOA) is non-zero alongside a deemed gain; silent when all are nil.
* `Sl.20 = 0` / `Sl.17 = 0` closing-WDV identity (287 / 298): applied only when there is no deemed
  gain; correctly skipped when one is present.
* Rate45 `blocked` branch in 280: in the new regime the expected Sl.10 is 0 (so a claim fires); in
  the old regime the expected Sl.10 is `ROUND(6 × 45%)` (so the same claim is silent).
* 281 is skipped for Rate45 by design — that schema block carries no half-rate leaves
  (`books/ITR-5/DPM_DOA.md`, "Rate45 quirk").

## Notes

**1. Rule 261 operand map verified end-to-end.** 261 was the one serial in this range added in the
census cleanup wave (`61_rules_enc_24.js`), so its seven P&L operands were checked individually
against `70_sec_pl.js`: `DebitsToPL.DebitPlAcnt.PBT` (54), `PersumptiveInc44AD.TotPersumptiveInc44AD`
(62ii), `PersumptiveInc44ADA.TotPersumptiveInc44ADA` (63ii), `TotalPrsumptvIncUs44E` (64v),
`NoBooksOfAccPL.TotBusinessProfession` (65iii), `NetIncomeFrmSpecActivity` (66iv),
`NonResidentPL.NetProfit` (67ii). With all six non-54 operands loaded (total 11,50,000) and BP A1
raised by exactly that amount, 261 is silent; with A1 left unchanged it fires. No operand is
silently dropped.

**2. Rule 282 co-operative sub-status list.** The encoded set `{4, 15, 16, 17}` maps, via
`GEN_SUBSTATUS_CODE` in `70_sec_gen.js`, to Other Cooperative Society, Primary Agricultural Credit
Society, Primary Co-operative Agricultural and Rural Development bank, and Co-operative Bank
(other) — i.e. exactly the co-operative sub-statuses the ITR-5 status list offers. Code 11
(Society registered under the Societies Registration Act) is deliberately **not** in the set: a
registered society is not a co-operative society, and the rule bars only firm/LLP/co-op. This is
the correct reading and is what the test above exercises.

**3. Observation (not a FAIL) — serial 270.** The census bucketed 270 OFFLINE-IMPOSSIBLE because
"sum of revenues in Schedule P&L / Trading Account" is not one field. The export does, however,
carry `TradingAccount.TardingAccTotCred` and `PARTA_PL.CreditsToPL.TotCreditsToPL`, so an upper
bound on `Σ A3` is arguably constructible. Same observation applies to 258. Flagging for the CEO;
neither is a firing defect in an encoded rule, and re-classifying them is a census decision, not
mine.

**4. Observation (not a FAIL) — serials 279 / 292.** Both are encoded *in substance* rather than
literally. A strict `Sl.20 = 5+8−3−4−7−19` would fire on the lawful reference block (where the
expression evaluates to −25,00,000 while Sl.20 is 0), because Sl.20 is a conditional deemed-gain
input, not a computed cell — the sheet itself does not compute it
(`books/ITR-5/DPM_DOA.md` row 20: "enter negative only if block ceases to exist"). Splitting it
into the conditional floor (285/296) and the ceased-block consequences (286/287 and 297/298) is the
behaviour a real return needs, and all five of those fire and stay silent correctly.

**5. Observation (not a FAIL) — the sibling `re_*.js` scenario fixtures trip A261.** All 53
regime/entity scenarios in `tests/ITR-5/verify/` set `S.bp.pbt` directly while leaving the P&L
schedule empty, so the return they build has BP A1 ≠ P&L Sl.54 and **A261 fires on every one of
them**. That is rule 261 working correctly on a genuinely inconsistent return — BP A1 is a free
input (`70_sec_bp.js:390`, `inpN("bp.pbt")`), not derived from the P&L, so this is reachable
through the UI and the rule must bite. But if those fixtures are meant to double as lawful
reference returns, they need their P&L profit-before-tax filled to match; as they stand, any
whole-return "0 Category-A errors" claim made from them would be wrong. `tests/ITR-5/state.js`
itself is clean (A1 = Sl.54 = 26,30,000, 261 silent).
