# ITR-5 · A.Y. 2026-27 — rule-firing verification, Category-A serials 1–50

Range: `books/ITR-5/rules.json` serials 1–50, all `cat:"A"`.
Encoded in: `forms/ITR-5/src/61_rules_enc_01.js` (single batch, no duplicate serial in any other
`61_rules_enc_*.js` — verified by grep of `A(n,` across all 24 batch files).
Driven against: `forms/ITR-5/Yukti_ITR5.html` (Playwright/Chromium, `file://`).
Lawful reference client: `tests/ITR-5/state.js` (S SUDHIR AND ASSOCIATES, resident partnership
**Firm**, OLD regime, 44AB audit case).

## Method

Two complementary harnesses, both reading `runRules(Object.values(buildReturn().ITR)[0], S)`:

1. **Engine-level** (`paint()` → `buildReturn()`): a state patch on top of `tests/ITR-5/state.js`,
   so the violation travels the real UI → state → exporter path. Used wherever the engine can
   actually emit the violating value. This is the authoritative test.
2. **Object-level** (crafted return): the lawful built return is deep-cloned and one field is
   mutated, then `runRules` is called on the clone. Used for the serials that guard against a
   hand-edited / portal-supplied return the engine itself will never emit (the brief explicitly
   permits this), and to isolate a single guard from collateral violations.

**Baseline:** the lawful reference client returns **0 Category-A and 0 Category-D** messages, with
no page errors. Every serial in this range is therefore silent on the lawful reference return; the
"silent-on-lawful" column below additionally records the *guard-off* test (guard not triggered while
the consequent is violated) and, where relevant, a *lawful-variant* return of a different entity type.

Conditional serials were tested on **both sides of the guard** as the brief requires. Entity-gated
serials were additionally run against a lawful return of every ITR-5 status/sub-status combination
(Firm, LLP, Local Authority, all four co-operative sub-statuses, Society, Business Trust, Investment
Fund, Trust-other-than-ITR-7, Any-other-AOP/BOI, Estate of the deceased, Estate of the insolvent,
Other AJP) to hunt false fires.

## FAILS

### **F1 — serial 15 FALSE-FIRES on a lawful return (AOP/BOI, Society sub-status)**

`61_rules_enc_01.js:67` —
`A(15,status!=="14"||["15","16","17","11","4","20","21","13","8"].indexOf(sub)>=0, …)`

**Scenario (engine-level, reproducible from the UI):** lawful AOP/BOI return whose sub-status is
`2-Society Registered under Societies Registration Act-1860 or any law corresponding to that State`
— i.e. `S.pi.status='14'; S.pi.substatus='2-Society Registered under Societies Registration Act-1860 or any law corresponding to that State '`
(the exact value the Sub-status dropdown puts in state), member table and Table-A Sl.B/Sl.D filled.

**Observed:** `runRules` returns Category-A **15** — "Status is 'AOP/BOI' — a valid Sub-status must
be selected and cannot be blank" — on a return where a valid sub-status *was* selected.

**Root cause is NOT in the rule.** The rule is correct; `PartA_GEN1.OrgFirmInfo.SubStatus` is never
written for this one sub-status. `forms/ITR-5/src/70_sec_gen.js:517` does
`const _sc=GEN_SUBSTATUS_CODE[st0(S.pi.substatus)]` — `st0` **trims** — while the map key at
`70_sec_gen.js:59` is `"2-Society Registered under Societies Registration Act-1860 or any law corresponding to that State "`
**with a trailing space** (it is also the dropdown's option value, `70_sec_gen.js:46`). The trimmed
lookup misses, `_sc` is `undefined`, and `SubStatus` is silently omitted from the return.

**Proof:** injecting the trimmed key (`GEN_SUBSTATUS_CODE['…that State']='11'`) before `paint()`
makes `SubStatus` export as `"11"` and serial 15 goes silent on the same return.

**Collateral (also in this range):** with `SubStatus` missing, serial **32** ("Society / Business
Trust / Investment Fund / Any other AOP-BOI → Table A Sl.B and Sl.D cannot be blank") can never fire
for the Society sub-status — blanking Sl.B and Sl.D on a Society return produces serial 15 instead
of 32. With the key fix in place the same return correctly produces serial 32. Serial 32's own
logic is sound (it fires and is silent correctly for sub-status `"8"`); only its Society branch is
dead.

*Fix belongs in `70_sec_gen.js` (trim the map key, or stop trimming at line 517), not in
`61_rules_enc_01.js`.*

### **F2 — serial 44 FALSE-FIRES on a lawful return (115BAE elected at A19 d(iv)b)**

`61_rules_enc_01.js:144` —
`A(44,!st0(FS.Form10IFADate)||FS.OptingTaxation115BAEYes==="Y", …)`

**Scenario (engine-level):** resident **Other Co-operative Society** (status `14`, sub `4`),
date of formation `01/05/2023`, date of commencement `01/06/2023`; A19 d(iv) "was the new
manufacturing co-operative society required to furnish a return for AY 2024-25 / 2025-26?" = **No**,
so the d(iv)**b** question "Do you wish to exercise the option u/s 115BAE …?" = **Yes**
(`OptingTaxation115BAENo="Y"`), Form 10-IFA date `01/09/2026` and acknowledgement number filled.
This is a fully lawful 115BAE election.

**Observed:** `runRules` returns Category-A **44** — "Form 10-IFA is filed — opting for the new tax
regime u/s 115BAE is mandatory" — although 115BAE *has* been opted. The identical return elected via
the d(iv)**a** branch (`OptingTaxation115BAEYes="Y"`) produces no Category-A message at all.

**Cause:** the guard accepts only `OptingTaxation115BAEYes==="Y"` and ignores
`OptingTaxation115BAENo==="Y"`, even though the same file's own helper on line 27
(`opted115BAE=(FS.OptingTaxation115BAEYes==="Y")||(FS.OptingTaxation115BAENo==="Y")`), used by
serials 19/34/36/37/47, treats both branches as "has opted 115BAE". Serial 44 is the odd one out.

### **F3 — serial 48 DOES NOT FIRE on the violation its own text states (wrong branch guarded)**

`61_rules_enc_01.js:152` —
`A(48,FS.OptingTaxation115BAEYes!=="Y"||(!!st0(FS.Form10IFADate)&&!!st0(FS.Form10IFAAckNo)), …)`

Source text (serial 48 + its continuation at 49): *"If option 'Yes' is selected for **'Do you wish to
exercise the option u/s 115BAE of Opting of New Tax regime in AY 2026-27'** at **A19 div(b)**, then
'Date of filing of Form 10IFA' and 'Acknowledgement number' at A19 div(c) are mandatory."*

A19 div(b) is the **`OptingTaxation115BAENo`** field (`70_sec_gen.js:283`, ref `F96 (b)`);
`OptingTaxation115BAEYes` is div(**a**) (`70_sec_gen.js:281`, ref `F92 (a)`). The encoded guard reads
div(a). The rule's own comment and message both say "at A19 div(b)", so the intent is clear and the
wiring is wrong.

**Scenario (engine-level):** same resident Other Co-operative Society as F2; A19 d(iv) = No →
d(iv)**b** = **Yes** (`OptingTaxation115BAENo="Y"`), Form 10-IFA date **and** acknowledgement number
**left blank**.

**Observed:** serial 48 is **silent**. Only serial 34 fires. Object-level variant (div(b) = Yes with
the 10-IFA date supplied but the acknowledgement number blank) is likewise silent for 48.

**Net effect:** serial 48 never fires for the case it is written for, and instead double-fires with
serial 34 on the div(a) case. Suggested wiring: guard on `FS.OptingTaxation115BAENo!=="Y"`.

## Gaps and observations (not scored as FAIL)

- **G1 — "blank" is tested as "key absent", not "empty object" (serials 1, 2, 10, 13).**
  `A(1/2/13,…,!!I.PARTA_BS&&!!I.PARTA_PL)` and `A(10,…,!!RG(I,"PARTA_BS.NoBooksOfAccBS")&&…)` are
  presence tests. A return carrying `"PARTA_BS":{}` / `"PARTA_PL":{}` (or `NoBooksOfAccBS:{}` /
  `NoBooksOfAccPL:{}`) passes all four silently, although the source text says "can not be blank" /
  "are required to fill in". The form's own exporter always emits populated blocks, so this is only
  reachable from a hand-edited / portal-supplied return — which is exactly the population these four
  serials exist to police. Deepening the test to "present **and** has at least one non-zero leaf"
  would close it.
- **G2 — serial 3 is silent when `MobileNo` is absent or `""`.** The guard is
  `!mob||/^[6-9][0-9]{9}$/.test(mob)`. Through the engine this is harmless (a blank mobile exports as
  `0`, which the rule rejects → it fires), but a portal return that omits the key entirely escapes.
- **G3 — serial 21 carries a ±1 tolerance** (`Math.abs(RSUM(...)-100)<=1`), so member shares summing
  to 99 or 101 pass. Defensible (33.33 × 3 = 99.99), just recording it.
- **G4 — serial 33 compares exactly `"YES"`.** That matches the schema enum
  (`enums.json`: `PartnerForeignCompFlg = [["YES","YES"],["NO","NO"]]`) and the engine's
  `GEN_BYN`, so it is correct — but a return carrying `"Yes"` or `"Y"` would slip through.
- **N1 — serial 9 could now be encoded.** It is uncoded, and the in-file note gives the reason as
  "the lawful test client's audit-report date (2026-09-20) is later than the environment's current
  date". As of today (2026-09-22) that is no longer true: the lawful client's
  `AuditReportFurnishDate` (2026-09-20) is *earlier* than the system date, so a faithful
  `AuditReportFurnishDate <= today` check would be silent on the lawful client and would fire on a
  future-dated audit report. Confirmed uncoded today: a crafted `AuditReportFurnishDate` of
  `2099-01-01` raises nothing. Flagging for the CEO's judgement — encoding it would make Gate 6 depend
  on the wall clock.
- **Out of range, for information only:** every AOP/BOI and AJP lawful variant tested also raises
  serials 124 and 165 (and 587 for AJP / Local Authority, 662 for AJP). Those sit outside serials
  1–50 and were not investigated here; whoever owns those ranges should check whether they are
  genuine (the chassis is a Firm-shaped return re-statused) or false fires.
